# 0159：按任务需要的方案与人工验收

状态：已采纳并完成限定实际验收。实施日期：2026-09-09；最终记录：2026-09-10。

## 问题

原Plan固定三个方向，单模块任务同时成为最后模块，强制填写六段人工说明。数量和文字非空不能证明方案有用或检查通过，却成为小任务的完成阻断。仅合并按钮无法消除后端和数据库中的这些要求。

## 决定

保留现有Plan、Selection、WorkItem和Thread续接，不引入第二套计划引擎。`plan_delivery.v1`允许1–3个有意义的方向，清晰任务优先一个。旧提案的规范序列化、指纹和请求身份不变。

人工验收策略由操作者在采用方案时选定，保存在不可变Selection的`manual_acceptance`。`required`保留原检查点要求；`on_demand`可自行添加人工记录，完成事项无需填写该表。旧记录和省略字段的旧客户端使用required；新Web明确提交on_demand默认值，提供逐项人工验收选择；CLI支持显式参数。模型提案没有设置策略的权限。

按需人工记录不免除事项状态、原模块内容/依赖、依赖完成、Deliver和现有权限约束。完成写入复用原人工检查点的模块一致性检查；SQLite验证待写入的新字段和依赖。真实命令、当前修改版本、报告和Finish仍走原门禁，人工说明不作为自动通过证据。

一次采用并进入交付复用两个现有API，各自保留原key。第一步成功、第二步未知时仅确认第二步，不重新选择、不自动启动执行。原收据确认优先于新动作的当前状态校验。

跨Run承接保留策略。required引用原人工检查点；on_demand引用原真实事项完成事件。两者都校验同Thread、相邻执行、精确模块和进度；不复制Job、检查点或自动通过。复用已有不可变事件投影，无新增完成账本。

## 兼容与代价

v156正常迁移重建提案表数量约束、增加选择策略并更新相关守卫；不修改已发布迁移和旧行。未加入人工门禁的旧历史仍保留原豁免含义，不把缺记录解释为新策略。

策略在选择后固定，不能事后用同key换模式；需要重新讨论的计划仍使用已有Plan流程。组合请求意图沿用当前QueryClient生命周期，跨应用重启持久化另行处理。数据库守卫与应用校验有重复，但分别保护实际写入与用户可理解的失败；不为这项简化再建可配置工作流框架。
