# Review workflow

Establish the exact review base before judging the patch. Resolve the intended merge-base and consume the complete merge-base diff, including commits, staged and unstaged changes, renames, generated files, submodules, and every affected path. When Git advanced evidence is available, reconcile the full diff with its stable hunk graph instead of sampling files or trusting a summary. State every unreviewed path or omitted byte.

Treat repository state as part of the change. Inspect detached HEAD and upstream identities, index and worktree digests, unresolved conflict files with base/ours/theirs object IDs, active rebase/cherry-pick/bisect state, stash roles, and all registered or unexpected worktrees. Check whether a stale preview, branch or remote drift, case collision, symlink or junction, and submodule boundary fail closed.

When `code-intel-lsp.v1` tools are available, use definitions, references, implementations, diagnostics, and call/type hierarchy to strengthen the trace. Preserve the Workspace/root, commit/dirty digest, document URI/hash/version, server generation, capability fingerprint, query fingerprint, and page source attached to the result. Treat `current` as language-server evidence only, disclose omissions on `partial`, refuse locations marked `stale`, and fall back to explicitly labelled text inspection on `unavailable`. Semantic output is never proof of authorization, test success, exploitability, or absence of defects.

Trace changed behavior through callers, callees, trust boundaries, and lifecycle states. Check initialization, normal operation, conflict, cancellation, retry, skip, abort, restart, cleanup, and recovery. For concurrent or durable code, inspect ownership, ordering, idempotency, generation fencing, approval binding, checkpoint atomicity, partial failure, crash reconciliation, and duplicate-mutation prevention. Follow shared schema, event, API, CLI, and Desktop consumers beyond the edited line.

Evaluate test strength rather than test presence. Identify what each check proves, false-positive gaps, missing negative or boundary cases, and whether the commit, configuration, operating system, filesystem semantics, and tool versions match the claim. Classify evidence as confirmed, inferred, or unverified.

Report actionable findings first, ordered by severity and exploitability, with precise paths, triggering conditions, impact, and supporting evidence. Avoid style-only findings unless they hide a defect. If no finding is confirmed, say so and list residual risk, skipped platforms, and untested recovery surfaces.

Keep review read-only unless the operator separately authorizes a change. Git advanced previews, hunk identities, conflict state, worktree inventory, and recovery receipts are evidence only; they do not authorize stage, revert, stash, history rewrite, bisect, or worktree mutation. Treat this Skill as guidance only; it grants no tool, filesystem, process, network, approval, or delegation authority.
